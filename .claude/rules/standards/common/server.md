# Common: Server Code

Rules for server code in Next.js (Server Components, Server Actions, Route Handlers, jobs), Node.js + Express, Node.js + NestJS, Node.js + Fastify and Node.js + Hono, on top of [typescript.md](typescript.md). A stack's `rules.md` adds to them and wins where it is more specific.

## Authorization and Security

- Deny by default: every route, handler and Server Action requires a session unless explicitly marked public; a test checks that every non-public endpoint rejects a request without a session.
- Authorization checks access to the specific resource (and its tenant), not just a session or a role.
- The user and tenant come from the session, never from client input; privileged fields (role, owner, tenant, status, prices) never come from input: input schemas list only the fields a client may write.
- The server computes prices, totals and time; the client sends only IDs and quantities.
- Passwords are hashed by the auth library, never logged or returned.
- Session cookies are `httpOnly`, `secure` and `sameSite=lax`, with the `__Host-` prefix (or the auth library's own `__Secure-`, as in Better Auth) unless subdomains share the session.
- Mutations with a cookie session check `Sec-Fetch-Site`, or `Origin` if it's absent: `same-origin`, `none` or an allowlisted `Origin` passes, and so does a request with neither header (a native app, a server).
- A new session is issued on login and on a privilege change; a password reset revokes all sessions.
- Login, signup and password reset respond the same whether or not the account exists; admin roles use MFA.
- Parameterized DB queries only, no SQL string concatenation; user input never ends up in table, column or alias names.
- The app connects to the DB as a user without superuser privileges.
- CORS uses an explicit origin allowlist, never `*` or a reflected origin with credentials.
- Security headers are set centrally: HSTS, `X-Content-Type-Options`, `Referrer-Policy`; HTML pages also get `Permissions-Policy` and a CSP.
- Rate limits per IP and per user on auth, signup, password reset, email-sending, AI and other public or expensive endpoints; the limiter store, the auth library's own included, is shared across instances.
- Better Auth's schema is generated by its CLI (`auth generate`) into the ORM schema and ships as a regular migration, regenerated after every Better Auth upgrade (a mismatch blocks auth at startup); its tables keep the CLI's column types and IDs, an exception to the `timestamptz` and `uuidv7` rules below.
- Behind a proxy, the trusted proxy is its addresses, or the exact hop count when the app can be reached only through the proxy; never "trust everything", so clients can't spoof their IP.
- Request body size is limited.
- Files are uploaded directly to private storage via presigned URLs that fix the content type and maximum size; the server generates the file key, checks the file type by its content after upload, and serves files through short-lived signed URLs, never from the app's own origin. The server receives a file itself only when unavoidable.
- A request to a user-supplied URL goes only to allowlisted hosts; where an allowlist is impossible (customer webhooks), private, link-local and metadata IP ranges are blocked after DNS resolution and every redirect is re-checked.
- Incoming webhooks verify the signature against the raw body and are idempotent.
- Tokens and signatures are compared via `timingSafeEqual`.
- Auth events, role and permission changes, data exports, deletions and admin actions go to an append-only audit table (actor, tenant, action, target, IP, time) with a defined retention.
- AI features require auth, a rate limit and a per-user token or cost cap; model and tool output and the chat history a client sends are untrusted input, and the server authorizes every tool call.
- A tool that waits for the user's approval gets it signed (`experimental_toolApprovalSecret` in the AI SDK, one secret for all instances), or a client can approve a call the server never requested.

## Multi-tenancy (multi-tenant projects only)

- Every tenant-owned table has a `tenant_id`; the tenant comes from the session.
- Queries are scoped to the tenant by one data-access helper or by Postgres row-level security, not by hand in each query.

## Database

- snake_case in the DB, camelCase in code; the ORM converts.
- Migrations are generated and committed; no schema sync without migrations (push) in production.
- Migrations run as a separate deploy step before the new version starts, never on app start; the exception is pg-boss's `migrate`, which stays on in the app to build the indexes its migration leaves to the background.
- Migrations are compatible with the previous code version (expand/contract: add first, remove in the next release).
- Migrations run with a short `lock_timeout`, so DDL waiting for a lock fails the deploy step, which is then run again, instead of locking the table for all queries.
- Integrity is enforced in the DB (foreign key, unique, not null, check), not only in code.
- Uniqueness is guaranteed by a constraint, and a violation is handled as a conflict error (409); a preceding SELECT doesn't guarantee it.
- Concurrent updates use an atomic UPDATE or a row lock, not a separate read and write.
- Fields used for filtering, sorting and relations have indexes.
- Related records change in one transaction: short, without external service calls; the service opens it and passes it to the data layer explicitly.
- No queries in a loop: related data is fetched in one query.
- Select only the needed columns.
- One connection pool per process, with an explicit limit, connection timeout and `statement_timeout`; closed on shutdown.
- Time is stored as `timestamptz`, a date without time as `date`, money as an integer in minor units.
- IDs exposed in URLs and APIs are `uuidv7` generated by the DB; sequential identity keys stay internal. In code, `crypto.randomUUID()`, not `Math.random()`.
- Every table has `created_at` and `updated_at`. Soft delete only where the product requires it.

## Performance and External Services

- No synchronous `fs`, CPU-heavy synchronous `crypto` (`scryptSync`, `pbkdf2Sync`) or other heavy computation in request handling.
- Anything long-running or that must not be lost goes to a job queue; the response doesn't wait for an email, report or third-party API.
- Every external service call has a timeout (`AbortSignal.timeout`); retry with backoff only for idempotent operations.
- Each external service has one client module, created once, not per request and not scattered across services.
- Independent operations run in parallel (`Promise.all`), except queries inside one transaction; parallel work over a user-sized collection has a concurrency limit.
- Large files and result sets are streamed, not loaded into memory in full.
- Caching is added after measuring, with an explicit TTL and invalidation.

## Background Jobs

- A job that must not be lost is enqueued in the data change's transaction (a Postgres queue) or through an outbox table; enqueueing after commit is only for best-effort jobs.
- The job handler is idempotent: a repeated run doesn't duplicate the effect.
- The payload holds only IDs; the handler fetches current data from the DB.
- Retry with backoff, an attempt limit and a timeout; permanently failed jobs are visible in monitoring.
- Periodic jobs run once across instances, through the queue scheduler or a lock, never `setInterval` or in-process cron.
- With Redis, the queue and cache don't share a client: the worker waits for Redis with no retry limit, while calls from HTTP fail fast. The queue's Redis runs without key eviction, so a cache with eviction lives separately.

## Logging and Observability

- Structured JSON logs only, to stdout; pretty output only in development.
- Every request has a request id, in all its logs and in the error response.
- `AsyncLocalStorage` carries only the request id, logger and trace context; the actor (user, tenant) is passed to services explicitly, so jobs and scripts run the same code.
- The `error` level is only for what requires action; expected 4xx aren't logged at it.
- No secrets or personal data in logs; the logger redacts sensitive fields.
- Error monitoring is initialized before the app code loads (`--import` for Node servers): in ESM, importing it from the entry point doesn't guarantee auto-instrumentation.
- Traces use OpenTelemetry: the W3C `traceparent` is propagated to outgoing calls and jobs, and the trace id appears in logs.

## Configuration and Startup

- Env is validated by a schema at startup; the app doesn't start with an invalid env.
- Only the typed config module reads `process.env`; locally, the runtime or framework loads env files, never `dotenv`; in deploy, env comes from the platform.
- The server runs in UTC.
- A self-hosted server has a liveness endpoint without dependencies and a readiness endpoint that checks the DB connection.
- A self-hosted server shuts down gracefully on `SIGTERM`: readiness starts failing so the load balancer drains, then it stops accepting requests, finishes in-flight ones, ends long-lived streams (SSE, WebSockets), stops the queue workers and closes the DB pool; a forced-exit timeout, shorter than the platform's grace period before `SIGKILL`, ends it.
- A self-hosted server's `keepAliveTimeout` exceeds the load balancer's idle timeout, otherwise random 502s.
- In the container, Node starts directly, not via the package manager, and not as root (`USER node` in the Dockerfile); `NODE_ENV=production`; only prod dependencies in the image.

## Testing

- The foundation is integration tests against a real DB, no ORM mocks; the test DB runs in a container with the same migrations.
- Access is covered by tests: another user, or another tenant, can't read or modify someone else's data.
